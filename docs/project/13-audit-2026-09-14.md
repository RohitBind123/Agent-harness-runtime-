## A. What we know

1. **This is a body of architecture and research, not a software system.** 94
   Markdown files, 11 DOCX, 9 SVG, 1 PDF, 5 Python files. All five Python files
   build or lint documentation.

2. **The design corpus is unusually complete and unusually well-argued.** 51
   handbook chapters with zero lint errors and zero unresolved cross-references;
   a specification at revision 5 with 39 checkable invariants and a 13-stage
   build order; four derived architecture documents each of which argues with
   the brief that commissioned it.

3. **The intellectual core is sound and consistent across documents.** The
   kind-typed claim; the observation log as the system of record; the world
   model as a projection; authority as authored configuration; the model
   proposing and never writing; standing earned by corroboration; verification
   before knowledge; the Principal Agent as a Run. These reinforce rather than
   contradict each other.

4. **The strongest single argument in the corpus is the cancellation example** —
   that perfect retrieval still hides a disagreement between a decision, an
   observation, and a test. It is the clearest statement of why this is not a
   RAG product, and it survives scrutiny.

5. **The engineering workflow is visible in git history** and has a consistent
   shape: read first, one complete artefact per commit, provenance markers
   preserved, findings recorded rather than resolved silently, external claims
   verified against primary sources.

## D. What is contradictory

Four, in descending order of how much they block.

### D1 — The product direction *(blocking)*

`prd.md` (2026-09-06) says **GO** on a macOS personal-paperwork agent and names
as non-negotiable: *"cut the terminal / Git / developer-tools environment from
the roadmap entirely."* The current strategic direction points at approximately
that segment. **The earlier argument has not been answered anywhere.** It may
not apply — a knowledge system is a different proposition from a file organiser —
but nobody has said so. → Q1, ADR-0021.

### D2 — The Memory and knowledge system Phase 1 schemas *(blocking any schema work)*

Memory **rejects** an entities table and a conflicts table for Phase 1 and
**defers** entity resolution. The knowledge system **requires** all three in Phase 1 and
calls entity resolution the component most likely to be underestimated.
**Neither document acknowledges the other**, and they use the same words —
`claims`, `evidence`, "Phase 1" — for different things. → Q7.

### D3 — Two runtime vocabularies, no stated normativity

The handbook and the specification describe overlapping concepts with different
names. Recorded as Finding A in September and still open. *"Two constitutions
with no stated relationship means every architectural argument can be won by
citing the other one."* → Q4, ADR-0002.

### D4 — The architecture is server-shaped; no named target is a server

Roughly half the kernel exists to arbitrate contention that does not exist with
one writer. Recorded as Finding C. The artefact that would resolve it — a
written single-writer invariant profile — does not exist. → Q8.

## F. What appears over-engineered

Stated as a principal engineer would state it, against the project's own
standard that fifty chapters are *"a library to draw from, not a backlog to
complete."*

| # | Over-built | Assessment |
|---|---|---|
| 1 | **The design-to-code ratio** | ~5,000 lines of specification and 51 chapters against zero code. The PRD's own estimate is that roughly **15%** goes in a first build. The risk is not the documents — it is that design work *feels like progress* and is more comfortable than the decisions that actually block |
| 2 | **The specification's "complete repository tree"** (~2,000 lines) | A fully-enumerated directory tree for a system that has never existed. Any tree specified before code is wrong in detail, and a wrong tree specified in this much detail invites being followed |
| 3 | **39 invariants for a single-writer system** | Leases, version-CAS, relay claims, sweepers, worker pools, per-tenant admission and budget ledgers arbitrate contention that does not exist in any named target. **The correct response is not to delete them but to write the profile (Q8)** — deleting the wrong half loses the correctness properties that are the entire point |
| 4 | **Multi-tenancy machinery for a single-team environment** | Correct for a product; premature for the first validation environment — and it is what keeps the *real* permission problem (overlapping audiences, §G2) invisible |
| 5 | **The evolution loop (8 chapters)** | Documented in the greatest depth of anything here and **furthest from buildable.** It is explicitly gated behind an evaluation harness that requires users that require a product |
| 6 | **The claim model's dimensionality, all at once** | Six kinds × two-axis authority × six temporal fields × a five-property predicate schema registry, **before a single observation has been ingested.** The model may be right; it is unvalidated in every particular. The mitigation is that Stage 1 exercises all of it on one source — but the risk of having designed to the wrong granularity is real |

**A defence of the corpus, which is also honest:** the specification-first
approach is what produced the finding that provenance and temporal fields cannot
be retrofitted, and that finding will save more than the documents cost. The
problem is not the depth. **It is that depth has been achieved in the areas that
were most enjoyable to specify, and not in the areas listed under G.**

## G. What appears under-designed

Ordered by how much damage the gap can do.

| # | Under-designed | Why it matters |
|---|---|---|
| 1 | **Overlapping permissions** | Named as a requirement — *"organizational knowledge is not partitioned; it is overlapping, per-source, and often per-channel"* — with **no mechanism designed.** And this is the one failure with **no error, no log line**, detectable only by a test. The most dangerous gap in the project |
| 2 | **Entity resolution** | Named *"the component most likely to be underestimated"* and then given roughly one section. No algorithm, no alias curation process, **no merge/split lifecycle** — and merges are inevitable with real data |
| 3 | **Admission** | Named *"the stage everyone omits"* and itself barely specified. *"Deterministic first, cheap model second"* is a shape, not a design. No rules, no thresholds, no worked example |
| 4 | **Extraction** | **The one place an LLM is unavoidable**, and there is no prompt, no output schema, no worked example, and no evaluation beyond "a reviewed sample." Everything downstream assumes its precision, and that precision is explicitly **NOT ESTABLISHED** |
| 5 | **Contradiction severity** | `blocking` versus `advisory` **gates actions**, and no rule assigns it |
| 6 | **Context assembly budget arithmetic** | The three un-droppable items are specified; the actual algorithm is not. "Budget and format" is a responsibility, not a design |
| 7 | **Knowledge-system-unavailable behaviour** | *"The read path never fails a step"* — but what a step does with **no** context is unspecified. Proceed with less? Abstain? The answer differs per capability and nothing says so |
| 8 | **The capability layer** | Seven capabilities named; **no typed signature written.** It is the thing that prevents an MCP rewrite later, and it has not been estimated |
| 9 | **The validation environment** | Entirely unspecified. See Q3 |

## I. What to build this way the first time

**None of the mechanisms below exists.** They are recorded as build requirements,
not as things to leave alone.

| Build it this way | Why |
|---|---|
| **The handbook and specification as derivation** | Do not rewrite them for a new product direction. Their value is that a decision can be traced to the argument that produced it |
| **The provenance markers** (`[AHE]` `[DAR]` `[INF]` `[BP]` `[FUT]`) | They separate evidence from inference, which almost no architecture corpus does |
| **`prd.md`, as a record** | Even if superseded. A superseded decision with its reasoning intact is worth more than a deleted one |
| **The kind-typed claim model** | The strongest idea in the corpus |
| **Observation log as the system of record** | Its rebuild property is the most valuable thing in the design and is cheap only if decided on day one |
| **The no-embeddings / no-graph / no-curation decisions** | Each has a real argument **and a pre-registered trigger.** A constraint that binds is working |
| **Tool projection as the knowledge system boundary** | Every access-control argument rests on it |
| **The clock discipline and its CI test** | Widen the allowlist per module with a comment; **never relax the test** |
| **Server-minted evidence handles** | A caller-chosen id is the whole attack |
| **The ACL predicate inside the store implementation** | Pre-filter, not post-filter |
| **"A model judgement may lower, never raise"** | The only thing that makes model judgement safe to use |
| **Identity-keyed extraction, first** | The one thing that does not retrofit |
| **The load floor and the retire floor outside the evolvable workspace** | Otherwise a loop moves the floor instead of improving the claims |

## J. Recommended next build step

**Collect twenty to fifty real questions from the project's own history, and
run Stage 1's exit test on paper — by hand, with no code.**

Concretely, in about a week:

1. Gather real questions people actually had to dig for. Not invented, not from
   a taxonomy.
2. For each, find by hand what the answer would need: which observation, which
   claim kind, which source class, which validity interval.
3. Write, by hand, the answer the knowledge system would have to produce — implementation
   fact, decision, author, date, and the gap between intent and reality.
4. Classify each question: **lookup**, **why**, **temporal**, or
   **contradiction**.
5. Derive the predicate vocabulary from step 2.

---

## K. Why that is the highest-value next experiment

**It tests the premise, not the implementation.** Every other candidate next
step assumes the thesis is right and proceeds to build. This one can falsify it.

**It produces five blocked artefacts as by-products:**

| Produces | Unblocks |
|---|---|
| Real questions | Q5 — the predicate vocabulary is supposed to be derived from them |
| The predicate vocabulary | Extraction, claim identity, contradiction detection |
| A held-out temporal question set | Stage 3's exit criterion, built from real history |
| Evidence on which source holds the answers | Q6 — which source is first |
| The lookup/why/temporal/contradiction ratio | The North Star's own falsifier |

**Step 4 is the one that matters most.** If the questions turn out to be
overwhelmingly **lookups**, then a good search box wins and the thesis is wrong
— and we learn it for the cost of a week rather than a year. That question is
recorded in the source material as **genuinely open**: *"most questions people
ask are lookups where retrieval quality is the whole game. The knowledge system's advantage
appears on WHY questions, TEMPORAL questions and CONTRADICTIONS — which are the
valuable minority."*

**It costs no code and blocks on nothing.** It does not need Q1 resolved, the
policy written, or the schema conflict settled. It can start today, and its
output makes three of those decisions easier.

**It has a built-in best-case test.** Question 2 from
`06-validation-strategy.md` §3 — *"which product are we building?"* — has a
known and uncomfortable answer: **two decisions in this repository disagree.**
If the hand-run knowledge system surfaces that contradiction from the documents alone,
the thesis is demonstrated on real data, on the project's own most important
open question.

**And it directly counters the failure the project is most exposed to**, named
in its own PRD: *"Building phase 1 beautifully, for four months, because it is
the part that is fully specified and therefore the most comfortable to build —
and arriving at phase 0's experiment far too late to act on the answer."*

---

## Summary in one paragraph

This project has an unusually strong and internally consistent architecture, no
code, and four unresolved contradictions — one of which (**which product**) is
blocking and has an argument standing against it that nobody has answered. The
design depth is real but unevenly distributed: the areas that were most
enjoyable to specify are the deepest, while permissions, entity resolution,
admission and extraction — the four places real data will hurt first — are the
thinnest. The right next move is **not** to build. It is to spend a week
answering, on paper and from real history, whether the questions this system
exists to answer are actually the questions people ask.
